DECISION: How a local-first Rust app should hold social-platform credentials and run scheduled publishing for one person, when the laptop may be asleep or offline at the scheduled time.
OPTIONS: Credentials: (A) macOS Keychain via the keyring or security-framework crates; (B) an encrypted file; (C) environment only. Authorization: (D) loopback-redirect OAuth with PKCE from the app; (E) device-code flow; (F) manual token paste. Scheduling: (G) the platform's native scheduler where it exists; (H) a local launchd agent that wakes and publishes; (I) post at approval time only, no scheduling.
CONSTRAINTS: One user, own accounts; Rust; local-first, no hosted server; every post approved first and published only for the exact approved revision; secrets never logged; tokens refresh unattended. As of October 2026, dated primary sources.
NEED: which of X, LinkedIn, Meta (Facebook, Instagram, Threads), YouTube, Bluesky, TikTok accept loopback http://127.0.0.1 redirect URIs for OAuth in development mode; which use rotating refresh tokens (a lost write loses access); which have native scheduling for each media type and its limits (delay window, edit and cancel, queue size); how launchd handles missed jobs after sleep; maintained Rust crates (oauth2, keyring, atrium) and their last release; idempotency (does any publish API accept an idempotency key, and how to avoid a double post after a timeout).
CURRENT EVIDENCE TO CONFIRM OR CORRECT (March 2026, unverified): only Facebook Pages had native scheduling; Instagram, Threads, X and LinkedIn APIs had none; TikTok scheduling was Business accounts only (20 minutes to 10 days ahead); YouTube schedules with private status plus a publish time; Meta and Threads tokens last 60 days; TikTok refresh tokens rotate.
WOULD CHANGE THE ANSWER: native scheduling on most platforms (then prefer G over a local daemon); a provider forbidding loopback redirects.
PUBLIC CONTEXT: Pre-launch single-user content studio.
