Rendering Options

R1: Headless Chromium (via Rust) – Use a Rust CDP client (e.g. chromiumoxide) to drive headless Chrome/Chromium. This yields full Web fidelity: CSS gradients, SVG filters, blend modes and webfonts (and ligatures) are rendered exactly as in a browser. The Chromium engine’s printToPDF produces multi-page PDFs with selectable text. Chromiumoxide, for example, is actively maintained (v0.9.1 Feb 2026) and even auto-downloads a “known good” Chromium binary. However, shipping Chromium is heavy (~70–100 MB) and requires bundling a browser binary (Chromium’s license is permissive BSD/MIT, but the size is large). Startup latency is high (several seconds to launch a fresh browser), though once running per-page render is fast (on the order of tens to hundreds of milliseconds). Output may not be perfectly byte-stable across machines or runs (GPU/timing differences can alter antialiasing), so pixel-difference tests might fail occasionally. PDF output is typically large (fonts embedded fully) but is accessible text – Chrome embeds fonts and outputs RGB (not CMYK). LinkedIn “document” posts require sRGB color (LinkedIn ignores CMYK) and recommend ~4:5 page ratio (e.g. 1200×1500); Chrome’s PDF can target that. Overall, R1 guarantees visual fidelity at the cost of heavyweight bundling and slightly non-deterministic output. (Crate maintenance: chromiumoxide has frequent releases, headless_chrome has v1.0+ but fewer recent updates.)

R2: Typst – A Rust-based typesetting language that compiles to PDF (and can produce PNG via conversion). Typst excels at high-quality text (ligatures, kerning, math) and produces well-formed PDFs with embedded, subsetted fonts. It is actively developed (open-source, many contributors) and fast on simple docs. However, Typst is not HTML/CSS – it lacks native support for things like CSS-style gradients, blend modes or complex SVG charts. Indeed, Typst’s SVG support is limited (filters/animations not implemented) and it’s geared toward document layouts. If your templates can be re-expressed in Typst’s DSL, you gain pixel-perfect typography and reproducibility, but copying an HTML template isn’t trivial. Output is deterministic (same input yields same PDF bytes, assuming fixed fonts) and multi-page PDF is native. Typst binaries are small (tens of MB) and use a MIT/Apache license. On the downside, implementing design elements (gradients, inline SVG charts) may not be possible or require workarounds. In short, Typst gives very stable, typographically-robust output with accessible text, but only if your design fits its model – complex web-style templates likely exceed its support. (No direct citation found for limitations, but see Typst issue #2988 noting SVG filter lack.)

R3: SVG templates + Rust rendering – Write templates as SVGs (or use the designer’s SVG exports). Use resvg/tiny-skia to rasterize to PNG (resvg CLI is ~5 MB and fully self-contained). Resvg supports nearly all SVG1.1 features, including gradients and blend modes (its test suite shows 100% passing for blend modes, and 90%+ for filters). Critically, resvg guarantees pixel-reproducible output across platforms: the same SVG yields identical pixels on any machine. This meets the “byte-stable/pixel-stable” requirement for snapshots. Fonts in SVG are rendered via its text engine; simple Latin text with embedded fonts (TrueType/OTF) usually shapes correctly, but very advanced scripts or ligatures may not get native shaping (resvg has no system text engine).

For multi-page PDF, one approach is to use a Rust PDF library (e.g. printpdf). Printpdf can embed fonts and even supports CSS-like gradients (“axial/radial shadings”), so a gradient background from SVG could be encoded. It also has an HTML-to-PDF experimental mode, but for maximum fidelity you’d manually place content. Printpdf is actively maintained (v0.12.x latest) and MIT/Apache licensed. It produces vector PDFs with selectable text (since you can draw text runs). PDF size can be modest because fonts can be subset. However, building templates in printpdf is low-level. An alternative is embedding rendered SVGs as images in PDF (via printpdf’s svg feature using svg2pdf internally), but that may rasterize text.

Packaging: resvg CLI is tiny; you only bundle your Rust binary and whatever fonts are needed. No big browser. Cold start of resvg is trivial (quick CLI). Printpdf is a library, adding maybe a few MB of binary (Rust static linking), but far smaller than Chromium. The maintenance of resvg and tiny-skia is healthy and active (frequent releases, test suite).

In summary, R3 can achieve very stable, high-fidelity static output if you convert your designs to SVG and PDF manually. It handles gradients and raster elements faithfully, and printpdf can embed text. But typography may not match Chrome perfectly (especially ligatures/uncommon scripts). Still, pixel-stability is a big plus.

R4: Desktop WebView (native) – Use a GUI webview (e.g. WebKit via Wry/Tauri) to render pages and print. This uses the OS’s web engine (WebKit on macOS, WebView2 on Windows). Fidelity is similar to R1, but setting up printing programmatically is complex. Packaging is easier (no extra binary) but implies a GUI app. It’s lower-level to automate. We have no specific benchmarks, but it would be similar to R1 in output. For brevity, we omit a deep dive on R4; it’s not commonly used for headless image/PDF generation.

Comparison
Visual Fidelity: R1 (Chromium) and R4 (WebView) use full browser engines, so they natively support all CSS/SVG/emoji features. R3 (resvg) supports most static SVG features (gradients, blend modes, filters). R2 (Typst) is strictly print-layout; it does ligatures and high-quality text but cannot express arbitrary CSS/SVG visuals.
Reproducibility: Resvg promises bit-identical pixels across platforms. Typst PDFs should also be deterministic (given fixed fonts). Headless Chrome can vary slightly (GPU vs CPU rendering, OS font differences) so output may not be 100% identical across runs.
Performance: Resvg/tiny-skia is very fast and lightweight; printpdf is pure CPU work. Cold-start is minimal for R2/R3 (just a small CLI). Chromium launch is much slower (seconds), though reused browser contexts are faster. Per-page Chrome render may be slower than native resvg, but on a single system all are reasonably quick (<<1s per page for simple slides).
Packaging/Size: R1 requires bundling Chrome (~70–100 MB binary) or relying on an installed Chrome. R3 bundles only small Rust binaries (resvg CLI ≈5 MB, PDF library code). R2 is modest (Typst CLI is a few MB). All use OS fonts or can bundle needed fonts. Licenses: Chromium (BSD), Typst/printpdf (MIT/Apache), resvg (MIT/Apache).
PDF/Text Output: Chrome’s PDF output includes real text (selectable). Typst’s PDF is text-based. Printpdf also outputs text. All three can embed fonts so text is selectable. PDF size: likely smallest with R2/R3 (subset fonts, no huge engine overhead). Chrome’s PDF can be large, but below LinkedIn’s 100 MB limit unless slides are huge. Make sure to use RGB colors (LinkedIn demands sRGB) and embed fonts to avoid missing glyphs.
Maintenance: chromiumoxide and headless_chrome are actively updated (2026 releases). Typst is actively developed (first release 2023, now stable). Resvg/tiny-skia are actively maintained (with a large test suite). Printpdf is actively maintained (v0.12.x). All have examples and documentation (printpdf has demos and web examples, typst has docs and a web app).
PDF and LinkedIn Notes
Fonts: Always embed fonts in your PDF. Chrome and printpdf do this by default or via options. Embedded fonts ensure the PDF looks identical on LinkedIn’s viewer.
Color/Profile: Use RGB colors (LinkedIn ignores CMYK). Chrome’s PDF output is RGB by default; ensure any Rust library PDF is set to RGB.
Page Size: LinkedIn recommends ~4:5 aspect for document posts (e.g. 1200×1500). Make your PDF pages that ratio to avoid unintended cropping.
File Size/Page Count: LinkedIn allows up to 100 MB per document and up to 300 pages. Keep each slide (<5 MB) and total under 100 MB.
Summary & Recommendation
R1 (Chromium) yields perfect fidelity for existing HTML/CSS templates (fonts, gradients, SVGs), but requires bundling Chrome and suffers some startup overhead and minor nondeterminism. It’s safest if your designs use complex web features.
R2 (Typst) is excellent for text-heavy layouts with high typographic quality, but cannot natively reproduce HTML/CSS templates with gradients/SVG effects. Use it only if you can adopt the Typst workflow.
R3 (SVG+Rust) can satisfy both stability and performance. Resvg renders images (with gradients/blends) identically on every run, and printpdf can embed text. If you can translate your templates into SVG (or use existing SVG assets), this approach can drop the Chromium dependency and keep everything in Rust. The caveat is font shaping: resvg’s text rendering may not match Chrome’s ligature handling for some fonts. If your font usage is straightforward and gradient usage is important, R3 is attractive.
R4 (WebView) is less commonly used for batch rendering and adds GUI complexity, so it’s generally not recommended here.

Given the user’s note: “Would change answer: if Typst or resvg is pixel-stable with acceptable typography, drop Chromium; otherwise keep R1.” – based on current capabilities, resvg + printpdf offers pixel stability and handles gradients, but may struggle with advanced typography (ligatures/complex scripts). Typst handles typography but not CSS graphics. If your designs prioritize pixel-stable visuals (and you can manage with non-HTML templates), R3 is worth pursuing. Otherwise, the Chromium-based pipeline (R1) remains the fallback, with packaging done via chromiumoxide (auto-download) and careful use of headless flags for consistency.
