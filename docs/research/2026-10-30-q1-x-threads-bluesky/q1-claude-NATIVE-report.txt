Publishing to your own X, Threads and Bluesky accounts from a local Rust app: what to build on (as of Oct 30, 2026)

Build on X’s pay-per-use API, a Threads app kept in development mode with only your own account as a tester, and Bluesky’s free XRPC API using an app password through a Rust SDK. None of the three blocks your plan. About 30 plain posts a month on X costs about $0.45. One that contains a link costs $0.20, x so 30 link posts cost about $6. Threads publishing to your own account works without Meta App Review. glamafacebook The real local-first problems are elsewhere: Threads only takes media from a public URL and needs an HTTPS, non-localhost redirect URI (Meta’s own sample app README says so), and X now restricts programmatic replies. x

TL;DR


X: Pay-per-use is the only option for a new developer. The Free tier closed to new sign-ups on Feb 6, 2026, and Basic/Pro are legacy plans. Budget $1–$10 a month and set a spending cap. Each post costs $0.015, or $0.20 if it contains a URL. Media upload uses the v2 endpoints, which pay-per-use includes. Use OAuth 2.0 PKCE with offline.access. Don’t build reply bots, likes, follows, quote-posts or a search/trends dashboard.
Threads: Keep the app in development mode and add yourself as a Threads Tester. Meta’s docs say testers can grant every permission “at any time”. App Review is only needed for users without a role on the app, so business verification isn’t worth pursuing. Budget engineering time for a 60-day token refresh and for public URLs to host images and video.
Bluesky: It’s free, needs no review, and the per-account write budget is generous. Start with an app password. Call createSession once and then refresh the session. Use bsky-sdk/atrium (pin 0.2.x/0.26.x, released Oct 27, 2026) or jacquard 0.12.x instead of raw XRPC, because rich-text facets and blob upload are fiddly. Treat atproto OAuth as a later upgrade: for a public, local-only client, the http://localhost client_id is a development exception, and sessions are capped at 2 weeks.

2. Auth model and token lifetimes

X (OAuth 2.0 Authorization Code with PKCE).


Access token: valid “for two hours”. X staff confirm on the forum that this is intended, and that refreshes also return expires_in: 7200. x
Refresh token: issued only when the offline.access scope is requested. x
Authorization code: must be exchanged “within 30 seconds”. twitter
Scopes: tweet.read tweet.write users.read media.write offline.access. A Feb 2025 forum token response shows exactly this set. x
Client type: PKCE supports public clients, so no secret needs to ship in the binary. x
Redirect URI: callback URLs have had to be pre-registered since Jun 12, 2018 (X changelog). x Explicit documentation of loopback (http://127.0.0.1:<port>) support was not found. Register a fixed-port loopback URL and test it.
Refresh-token rotation: not found as a documented rule. Always persist the newest refresh token returned.
Migration path: a token-exchange grant converts OAuth 1.0a tokens to OAuth 2.0 without re-consent (X changelog, Sep 21, 2026). x


Threads (Meta OAuth).


Endpoints: authorize at threads.com/oauth/authorize, exchange at graph.threads.com/oauth/access_token. facebookfacebook
Authorization codes: valid 1 hour. facebook
Tokens: short-lived tokens last 1 hour. Long-lived tokens last 60 days and can be refreshed when “at least 24 hours old but have not expired” (Meta long-lived-tokens doc, accessed Oct 30, 2026). facebookblotato
Permission grants: for public profiles, grants last 90 days and are extended on refresh. facebook Meta’s pages conflict on private profiles. The Get Started page says private-profile grants “cannot be extended”. The long-lived-token page says private-profile tokens “can now be refreshed” and their grants last 90 days. facebookfacebook Assume re-consent every 90 days if your profile is private. blotato
App secret: the code exchange needs the Threads app secret. facebookfacebook A desktop app therefore has to hold it. That’s acceptable for a personal app; keep it in the OS keychain.
PKCE: not found in the Threads docs.
Redirect URI: must exactly match a registered URI (Meta may add a trailing slash). facebookfacebook Meta’s developers.facebook.com reference pages don’t state the HTTPS/localhost rule, but Meta’s own sample repo does. The fbsamples/threads_api README says “Threads apps do not support redirect URLs with using localhost so you must map a domain to test locally” and “OAuth redirects are only supported over HTTPS so you must create an SSL certificate”. Plan for an HTTPS redirect, either a static page that displays the code or a tunnel. Since tokens live 60 days and refresh without a browser, this is a one-time annoyance.


Bluesky.


App password option: createSession with the app password returns access and refresh JWTs. Bluesky’s scopes guide says “There are currently no plans to deprecate either the transition scopes or the use of App Passwords” (atproto.com, accessed Oct 30, 2026). atproto An older OAuth roadmap discussion describes them as deprecated, so the official messaging is inconsistent. github
OAuth requirements: the atproto OAuth spec (page states “As of October 2026”) mandates PKCE S256, PAR and DPoP with server nonces. Refresh tokens are “generally single-use”, so they rotate. atproto
OAuth token lifetimes: access tokens should last under 30 minutes (15 minutes maximum if they can’t be revoked). Public clients get session and refresh-token lifetimes of up to 2 weeks. Confidential clients get unlimited sessions with 180-day refresh tokens, but that requires a hosted JWKS and signing key. atprotoatproto
Localhost option: a desktop app can use the http://localhost client_id with a redirect http://127.0.0.1/... (port ignored), which is a public, native client. atprotopypi Authorization servers are “encouraged to support this exception - including in production environments - but it is optional.” atproto
Scopes: atproto plus transition:generic. github Granular repo:/blob: permissions are rolling out. atprotogithub

You invite your own profile under App roles → Threads Tester and accept the invite in Threads settings → Website permissions. facebooknpmjs Typical review duration and whether a solo developer passes business verification: not found in primary sources. It’s irrelevant to your use case, so don’t pursue it.

5. Policy constraints


X (Developer Guidelines, accessed Oct 30, 2026):

Automated accounts must enable the “Automated” label, disclose the operator in the bio and link to a human-managed account. x
“AI-Generated Content & Replies” requires prior approval from X before deployment, and “Deploying AI-generated replies without approval is a violation.” x
Prohibited outright: non-API automation (results in permanent suspension), training AI/ML on X data, identical cross-account posting, and unsolicited mentions. x
Data handling: X content must be deleted within 24 hours when requested. x
Your situation: in a Rules and Policies forum thread about AI-drafted, human-approved scheduled posts on a brand account, the reply said to enable the Automated label. x That’s a forum answer about one app, not policy text. My recommendation: publish at the moment you approve, which makes it a user-initiated post. That keeps your personal account clearly outside “automated account” territory. If you add delayed scheduling, file a Policy Support request. X’s rules require no per-post AI disclosure for text (not found in primary sources).
Paid promotion: a paid_partnership flag exists for posts that contain paid promotion (Jun 3, 2026). x



Threads: the API overview limits use to publishing on a person’s behalf and displaying “those posts within your app solely to the person who created it”. facebook That fits a personal studio. Threads-specific rules on AI-content labeling or automation for API posts: not found in primary sources reviewed.
Bluesky: no developer terms on automation or AI labeling were reviewed in primary sources (not found). The documented constraints are rate limits and bot-like behaviour such as mass following and liking. bsky

Recommendations


X: build on pay-per-use now.

Implement PKCE with a loopback redirect, offline.access, a 2-hour refresh, and storage of the newest refresh token.
Use v2 chunked media upload plus /2/media/metadata.
Set a $10 monthly spending limit.
Avoid URLs in post bodies where possible, since each one costs $0.20. One option is to put the link in a later reply, but test first whether self-replies pass the “summoned” rule.
Publish on approval, not on a timer, unless you get X policy clearance.



Threads: stay in development mode forever.

Register an HTTPS redirect once and refresh the long-lived token every 30–50 days, from a background task when the app is opened.
For media, upload each file to a short-lived public URL (e.g. presigned object-storage URL) just before creating the container. This is the one unavoidable bit of hosted infrastructure. Text-only posts need none.



Bluesky: app password + bsky-sdk 0.2.x pinned (or jacquard 0.12.x).

Persist the session and refresh it, never re-login per post.
Use the SDK’s RichText to generate link and mention facets.
Revisit OAuth (jacquard’s loopback helper) once granular repo:app.bsky.feed.post scopes are standard.



Not worth building: Meta App Review, X Basic/Pro, OAuth 1.0a, v1.1 media, reply or engagement automation on X, trends and search dashboards, and cross-platform analytics beyond your own post counts.
