Local-first scheduled publishing for one person: credentials, OAuth and scheduling on macOS (evidence as of Oct 30, 2026)

Recommendation: store credentials in the macOS Keychain (A). Use loopback-redirect OAuth with PKCE (D) wherever the platform allows it. For scheduling, use a hybrid: native scheduling (G) only for YouTube and Facebook Pages, and a local launchd agent (H) for X, Instagram, Threads, LinkedIn, Bluesky and TikTok, with a supervised “publish on wake” fallback (I) when a slot was missed. Only two of the eight surfaces have documented API scheduling, and no provider was found that forbids loopback outright. So neither of the conditions that would change this answer holds. Meta is the one exception to watch, because it requires HTTPS outside development mode.

TL;DR


Credentials: use A, the Keychain. Store one Keychain item per account holding the full token bundle. As of the 4.x line, use keyring-core 1.x plus apple-native-keyring-store 1.0.2 (keychain feature, docs.rs dated 06 Aug 2026) rather than keyring v3 feature flags. X, TikTok and Bluesky rotate refresh tokens, so every refresh must be written durably before the new token is used. Environment variables alone (C) cannot persist rotated tokens, so rule them out.
Authorization: D almost everywhere. Google, TikTok (desktop) and Bluesky accept loopback with any port. X requires an exact-match http://127.0.0.1 callback, so use a fixed port. LinkedIn documents HTTPS redirects, but its own sample uses http://localhost:8080, and it gives refresh tokens only to approved partners, so expect a manual re-authorization every 60 days. For Meta, a one-time manual token exchange (F) is pragmatic: long-lived Page tokens have no expiration date, and Instagram and Threads tokens refresh every 60 days. Of these platforms, only Google offers a device-code flow (E), and only with the broad youtube scope.
Scheduling: native scheduling is rare. YouTube (privacyStatus=private plus status.publishAt) and Facebook Pages (scheduled_publish_time) schedule server-side. Meta’s current Pages guide says 10 minutes to 30 days, not 75. Everything else must be fired locally. launchd’s StartCalendarInterval catches up after sleep but not after power-off, so the agent needs a missed-slot policy, an approved-revision hash check, and per-platform duplicate checks, because none of these APIs offers a documented idempotency key.

4. macOS launchd behaviour


StartCalendarInterval: “Unlike cron which skips job invocations when the computer is asleep, launchd will start the job the next time the computer wakes up. If multiple intervals transpire before the computer is woken, those events will be coalesced into one event upon wake from sleep” (launchd.plist(5), current Xcode man-page mirror). github
Powered off: “if the machine is off when the job should have run, the job does not execute until the next designated time occurs” (Apple, Scheduling Timed Jobs, archive doc © 2003–2016). An Apple forum answer confirms that asleep and off are treated differently. appleapple
StartInterval: “If the system is asleep during the time of the next scheduled interval firing, that interval will be missed due to shortcomings in kqueue(3)”. This changed from the 10.9-era man page, which promised catch-up. Do not use StartInterval for publishing. githubapple
Dark wake caveat: an Apple developer-forum thread (#815034) reports that jobs can run during a lid-open DarkWake. Apple DTS (Quinn) says “launchd doesn’t guarantee anything about the power state of the system when it starts your job”. The job must therefore check network reachability itself. apple
Waking the Mac: pmset schedule wake|wakeorpoweron "MM/dd/yy HH:mm:ss" schedules one-time events (pmset(1)). Only one repeating on/off pair is allowed. dssw It needs root, so a per-user agent cannot set it without a privileged helper. IOPMSchedulePowerEvent, Power Nap limits, closed-lid-on-battery wake behaviour, and the rule that a LaunchAgent runs only inside a logged-in user session were not verified from primary sources in this research. Treat them as known-but-unconfirmed.


What this means: H works for “laptop asleep at slot time” (it fires late, on wake) but not for “laptop off”. The agent therefore needs a per-platform staleness policy. Example: publish late if under N minutes overdue, otherwise mark the post “missed” and require one-click re-approval (I).

Keychain caveat: legacy keychain items carry an access-control list tied to the creating binary’s code signature. An unsigned or re-signed dev build, or a separate launchd helper binary, can trigger “allow access” prompts that block unattended runs. Sign the app and its agent with the same identity, or have the agent be the same binary. This is a known platform behaviour; no primary citation was gathered here.

Recommendations


Credentials: A. Use keyring-core + apple-native-keyring-store (keychain feature), or security-framework directly if you need explicit ACL control. Store one JSON bundle per account (access, refresh, expiry, DPoP key for Bluesky). Hold a process-wide lock across refresh → write → use. Never log request bodies or Authorization/DPoP headers, and redact the token fields in error types. B (an encrypted file) is a fallback only for headless CI. C is unsuitable.
Authorization, per platform:

YouTube: D on an ephemeral loopback port. Move the consent screen to In production before relying on scheduling, otherwise refresh tokens die after 7 days. nangogoogle E is possible with the youtube scope but buys nothing on a laptop.
X: D with fixed http://127.0.0.1:<port>/callback, PKCE and offline.access.
TikTok: D (desktop loopback, wildcard port, hex PKCE). Until the app passes audit, posts are private-only, per TikTok and third-party docs. ayrsharetiktok
Bluesky: D via jacquard-oauth loopback. Expect 2-week re-auth as a public client. atproto App passwords are the alternative, but their session-refresh behaviour was not verified here.
LinkedIn: D with http://localhost per LinkedIn’s sample. Schedule a re-auth reminder at about day 50, because non-partner tokens cannot refresh. microsoftaws-sensei
Meta (Pages, Instagram, Threads): D in development mode if localhost works, otherwise F. Paste a short-lived token once, exchange it in-app for the long-lived Page token (no expiry) or the 60-day IG/Threads token, and auto-refresh the latter every ~7 days. facebookfacebook



Scheduling, hybrid:

G for YouTube (upload as private with publishAt at approval time) and Facebook Pages (≤30 days ahead, otherwise hold locally until inside the window).
H for X, Instagram, Threads, LinkedIn, Bluesky and TikTok. Use a StartCalendarInterval LaunchAgent that runs every few minutes plus RunAtLoad, re-checks the approved revision hash, and publishes only if the stored content hash matches.
I as the safety valve: if a slot is overdue beyond a per-post tolerance (because the Mac was off or offline), do not auto-post. Surface it for one-click re-approval.
Optionally add a root helper that sets pmset schedule wake before critical slots.



Exact-revision guarantee: bind every approval to a content hash covering text, media file hashes and platform options. Natively scheduled items are uploaded once at approval. Any later edit must cancel the remote schedule (FB DELETE, YouTube update/delete) and require re-approval.


Caveats


Many official pages showed no last-updated date. Dated items: Instagram refresh reference (Jul 17, 2025), apple-native-keyring-store 1.0.2 (Aug 6, 2026), jacquard 0.12.1 (Jun 26, 2026), the atproto OAuth spec (references October 2026), and Apple’s Scheduling Timed Jobs (archived 2016).
Several findings come from developer forums or third-party guides rather than primary references: X refresh rotation and the 6-month lifetime, X duplicate-content rejection, Threads/Instagram/X/LinkedIn having no scheduling, the TikTok 10k-follower eligibility, and Meta’s localhost-in-dev-mode exemption.
Facebook’s scheduling window conflicts between Meta pages (30 vs 75 days). Use the stricter one.
Not researched to primary-source level: Power Nap, IOPMSchedulePowerEvent, LaunchAgent login-session scope, atrium-api/bsky-sdk/reqwest/security-framework exact versions, Bluesky app-password refresh, LinkedIn native-PKCE enablement, and Instagram/Threads loopback rules.
